# 框架结果不可复现性分析(2026-09-02)

> 问题:相同配置 + 相同数据集 + 相同 seed,结果存在波动/偶然性。为什么?是否影响我们的结论?
> 结论先行:**根因是模型自研聚合代码里的 `index_add_`(GPU 原子累加)非确定性 + 早停机制的放大**;噪声幅度(val ~0.1pp 典型、最差 0.7pp;test ~0.3pp 典型、最差 2.3pp)与 P2 部分小效应同量级,**3-seed 均值结论不受影响,单-seed <0.2pp 的差不能下结论**。

## 1. 现象量化(数据全部来自已有结果,未重训)

### 1.1 天然重跑对(P1 screen vs P1 confirm:同 config、同 seed42、独立进程,23 对)

| 统计量 | val Δ | test Δ |
|---|---:|---:|
| mean \|Δ\| | 0.07pp | 0.26pp |
| std(Δ) | 0.15pp | 0.56pp |
| max \|Δ\| | 0.69pp(Movies B2) | 2.34pp(Movies B2) |
| 精确 0.0000 的对数 | 15/23 | 8/23 |

- Reddit-S 8/8 对全部逐位一致;Movies/ele-fashion/Grocery 部分对出现 0.03-0.69pp(val)、0.09-2.34pp(test)的差。
- 例:ele-fashion F1R1 seed42 val 0.8779(screen)vs 0.8765(confirm)= **−0.14pp**;Grocery F1R0 test −0.79pp;Movies B2~F1R1 val −0.69pp/test +2.34pp。

### 1.2 受控实验(同 GPU、连续运行)

- 同一 checkpoint 在 GPU 上 forward **5 次**:max |z_i − z_0| = **1.7-1.9e-6,不逐位一致**。
- 同 checkpoint、**空图 forward 5 次(无 index_add 路径):全部精确 0.0**。
- 30-epoch 同配置同 seed 连跑两遍:val/test 完全相同(噪声是**间歇性**的,短训练未触发)。

## 2. 根因

1. **主因:`index_add_` 的 GPU 原子累加顺序不定**。出现在 `relation_weighted_mean`(P1/P2 每次 forward 都调用)、`relation_mass`、`neighbor_mean`、`compute_node_relation_confidence`。atomicAdd 的完成顺序由 CUDA 线程调度决定,与 RNG seed 无关 → `set_seed` 无法控制。空图对照实验证明:**我们的栈里 cuBLAS GEMM 在同进程内是确定的,噪声全部来自 index_add 路径**。
2. **放大器:早停(checkpoint 按 val Acc 离散比较)**。1e-6 级的逐 step 差异在 200-300 个优化步中累积,偶发地让某个 epoch 的 val Acc 翻转(2 位小数边界)→ checkpoint epoch 不同 → 最终权重不同 → run 级差 0.03-0.7pp(val)/最高 2.3pp(test)。Movies 训练曲线最颠簸,所以 Movies 的 run 级噪声最大。
3. **次要可能**:跨进程 cuBLAS kernel 选择(指针地址不同)也可能引入 GEMM 噪声——但受控双跑与空图测试未观测到,故定性为"可能存在的次要来源"。
4. 框架 `set_seed` 只种了 random/numpy/torch/cuda RNG——**RNG seed 无法控制算子的原子序**,这是本质原因,不是协议 bug。

## 3. 对已有结论的影响评估

噪声参考线(取 1.1 的典型值):val 单-run 差 **<0.2pp 不可信**,test **<0.3-0.5pp 需谨慎**;跨 seed 均值差的标准误 = 跨 seed std/√3。

## 4. 修复选项(按侵入性排序)

1. **协议判读规则(立即采用,零改动)**:所有单-seed 差 <0.2pp 不作为证据;报告 3-seed 均值时保持 ±std;关键小效应(如 composition_uot)如需加强证据,补 seeds 或补同 seed 重跑取均值。
2. ~~确定性聚合:CSR 稀疏矩阵乘(torch.sparse.mm)~~——**已被实测推翻**(2026-09-03):cuSPARSE SpMM 内部同样走 split-K 原子归约,`use_deterministic_algorithms` 下同进程重复调用都不 bitwise 一致;torch-scatter 基于同类原子原语,不抱期望。**实际可行方案是已实现的 Hillis-Steele 固定顺序分块扫描**(见 §6),代价是 epoch 慢 5-10×,仅作 opt-in 验证模式,不进默认训练路径。
3. **全局确定性开关(严格复现用,不建议日常开)**:`torch.use_deterministic_algorithms(True)` + env `CUBLAS_WORKSPACE_CONFIG=:4096:8`(缺 env 时 matmul 直接报错,已实测)。注意:只靠聚合修复**不够**——GEMM 的跨进程非确定性也必须靠此开关管住(实测双跑在只修聚合后仍发散)。

## 5. 为什么之前没发现

- 主表一直用 3-seed mean±std,噪声被 std 吸收;
- 多数自然重跑对(15/23 val)恰好逐位一致,间歇性特征掩盖了问题;
- 直到用户对"同 seed 不同结果"敏感,才追溯到 screen vs confirm 的 0.1pp 级差。

## 6. 确定性验证模式(2026-09-02 追查,`p2.deterministic=true`)

按 §4 选项 2/3 实施后,逐步排查发现了**三条独立的非确定源**(全部实测定位):

| 源 | 定位方式 | 处置 |
|---|---|---|
| `index_add_` 原子累加(自研聚合) | 空图 forward 5 次 bitwise 一致 vs 带图 1.7e-6 | 确定性函数替换 |
| `torch.sparse.mm`(cuSPARSE) | **即使 use_deterministic_algorithms 下,same-process 重复都不一致** | 弃用 |
| `torch.cumsum`(CUDA) | 200K 元素稳定,但 **1.2M 元素 float32 跨进程差 1/16-1/32 量子**(= 1e6 量级 float32 ulp;decoupled-lookback 跨块前缀经原子序) | 弃用 |

**最终方案**:`_csr_chunk_aggregate` = stable argsort + **Hillis-Steele 分块扫描**(纯 elementwise/切片,累加顺序完全由代码固定)+ 串行跨块前缀(block 总量取扫描末行,连 `torch.sum` 归约都不用)+ `torch.use_deterministic_algorithms(True, warn_only=True)` + `CUBLAS_WORKSPACE_CONFIG=:4096:8`(管住 GEMM)。

验证链:同进程 forward ×10 bitwise 一致 → 跨进程 forward bitwise 一致 → **完整 300-epoch 训练双跑 results.json 逐位一致** ✓。45 tests 全绿。

用途与限制:
- **仅验证/消融用**(`p2.deterministic`),默认训练路径(原子版)不变、更快;
- warn_only 下 cumsum 若被引入新代码需重新验证(无保证);
- Hillis-Steele 的求和树与串行顺序不同 → 数值与原子版有 1e-6 级差异,与 CPU 串行参考亦有差异——**确定性,但不等于"更正确"**;
- sweep 期间 GPU0 有用户 vLLM(17.3GB),大图 run 固定在 GPU1。
