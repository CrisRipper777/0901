# 二十一、还有一个实验 driver 的并行调度风险

`run_p1_screen.py` 是：

```python
ThreadPoolExecutor(max_workers=len(gpus))
```

然后提前用轮询方式给每个 job 指定 GPU 0/1。

问题在于 ThreadPoolExecutor 的 worker 并不绑定 GPU。

可能发生：

1. GPU1 上的 job 先结束；
2. executor 取队列下一个任务；
3. 这个任务预先被分配的是 GPU0；
4. GPU0 原来的任务还没结束；

于是：

两个 process 同时跑 GPU0，GPU1 空闲。\boxed{ \text{两个 process 同时跑 GPU0，GPU1 空闲。} }

结果指标一般不会被改变，但：

- peak memory；
- runtime；
- OOM 风险；

会受影响。

P2 前建议改成：

> 每个 GPU 一个固定 worker queue，

或者 per-GPU semaphore。

# 二十三、还有一个对 P2 非常重要的数学提醒

你报告里写：

> transport plan 的熵正则天然防止 uniform 退化。

这个表述是反的。

标准 entropy-regularized OT 中，熵项通常会：

鼓励更平滑、更 diffuse 的 transport plan\boxed{ \text{鼓励更平滑、更 diffuse 的 transport plan} }

而不是防止 uniform。

而你现在 P1 代码：

```python
loss += alpha_entropy_weight * (-entropy)
```

若：

λ>0,\lambda>0,

最小化：

−H(α)-H(\alpha)

同样是在**提高 entropy**，把 alpha 推向更均匀。

所以以后如果 P2 要解决：

α→Uniform\alpha\rightarrow Uniform

不能说：

> 加 entropy regularization。

真正可能有帮助的是：

- cost structure；
- marginal constraints；
- UOT mass relaxation；
- smaller entropy temperature ϵ\epsilon；
- factor-relation diversity；
- 或显式 null/no-transport mass；

而不是单纯增大 entropy。
